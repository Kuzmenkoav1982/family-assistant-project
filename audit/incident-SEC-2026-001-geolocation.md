# SEC-2026-001 — геолокация членов семьи была доступна без аутентификации

Статус: **уязвимости закрыты, геолокация выключена, инцидент под
наблюдением.** Решения по разделам 9–11 приняты 11.09.2026. Вопрос
уведомления регулятора и затронутых семей остаётся открытым и
пересматривается при появлении любого признака эксплуатации.

Классификация: неавторизованный доступ к данным о местоположении,
в том числе несовершеннолетних. Категория, при которой «мы всё
исправили» не является достаточным ответом.

---

## 1. Что было доступно

### 1.1 `location-history` — история перемещений по подобранному `member_id`

`GET /?member_id=<uuid>&date=YYYY-MM-DD` без токена возвращал `200`
и полный трек участника за день: широта, долгота, точность, время.

Проверок не было вообще — ни сессии, ни семьи, ни субъекта.
Собственный `tests.json` функции закреплял утечку как ожидаемое
поведение: тест «Get history for member» ожидал `200` на конкретный
`member_id` без заголовков.

### 1.2 `geofences` — геозоны всех семей платформы

`GET` без токена: `200` и список **всех** геозон **всех** семей
(`SELECT ... FROM geofences ORDER BY created_at DESC` без `family_id`).
Геозона — это, как правило, дом, школа или детский сад с названием,
заданным родителем: «Дом», «Школа», «Садик». То есть адреса.

`DELETE /?id=<int>` без токена удалял любую зону по числовому id:
перебор `1..N` стирал геозоны всех семей.

`POST` без токена создавал зону без `family_id` — она попадала
в общий список и была видна всем.

### 1.3 `geofence-notifications` — рассылка по всей платформе

`POST` без авторизации. Адресаты подписок выбирались запросом
`WHERE u.id::text != member_id AND ps.active = TRUE` — **без**
`family_id`. То есть уведомление «⚠️ вышел из зоны "Школа"»
рассылалось бы подписчикам чужих семей.

Фактически не сработало: запросы шли к таблицам без префикса схемы
и к несуществующим колонкам (`ps.p256dh`, `ps.auth`, `ps.active`),
поэтому функция падала в `500`. Рассылка была нерабочей всё время
существования — это единственная причина, по которой утечки
уведомлений не произошло. Полагаться на такую защиту нельзя.

### 1.4 `family-tracker` — сверка с геозонами чужих семей

`check_geofence_violations()` читала `SELECT ... FROM geofences`
без `family_id`: координаты участника сверялись с геозонами **всех**
семей, и в `geofence_events` писались события по чужим зонам.

### 1.5 Смежное: `family-tracker`, `family-tracker-members`

Токен проверялся, но семья определялась `WHERE user_id = %s LIMIT 1`
без учёта `member_status`, а списки отдавали всех участников семьи
без адресной проверки. Не утечка наружу, но нарушение модели доступа.

## 4. Признаки эксплуатации

**Вывод: признаков эксплуатации не обнаружено, но доказать отсутствие
эксплуатации невозможно.** Журналов запросов за период уязвимости нет.

Что проверено:

| Источник | Период | Итог |
|---|---|---|
| `authz_audit_log` | 09.09 — 11.09.2026 | заведён в этой миграции, период уязвимости не покрывает |
| `security_audit_log` | 2 записи, 15.01.2026 | пусто по существу |
| `rate_limit_log` | 17.01 — 01.09.2026, 261 запись | только `action_type='auth'`, геозапросов не фиксирует |
| `analytics_events` | с 08.05.2026, 63 записи | продуктовые события фронта, не запросы к API |
| `product_events` | с 19.06.2026, 86 записей | то же |
| `geofence_events` | 0 записей | — |

Ни один журнал не содержит обращений к `location-history`:
функция ничего не логировала, а платформенные логи облачных функций
за 199 дней недоступны.

Чего поэтому **нельзя** установить:

- были ли обращения без токена;
- был ли перебор `member_id` (последовательный или по словарю);
- обращались ли к нескольким семьям с одного источника;
- кешировались ли ответы CDN или прокси (`Access-Control-Allow-Origin: *`
  и отсутствие `Cache-Control` этого не исключают).

Смягчающее обстоятельство: `member_id` — UUIDv4, слепой перебор
непрактичен. Но UUID участников **попадали в ответы других API**
(`family-tracker-members` отдавал `id` всех участников семьи), поэтому
для того, кто однажды имел доступ к любой семье, идентификаторы не были
секретом. Модель «UUID как секрет» здесь не работает и не должна
рассматриваться как защита.

## 6. Новая политика доступа к перемещениям

Доступ к точным координатам человека требует **всех** условий:

```
действующая серверная сессия
  + субъект в той же семье
  + субъект в статусе active
  + (это я сам  ИЛИ  подтверждённая связь со ЯВНЫМ scope 'geolocation')
  + запись просмотра в аудит
```

Реализовано как `auth_guard.require_location_access()` — единственный
законный вход к геоданным.

Что изменено принципиально:

1. **Роль больше не открывает координаты.** Из `ROLE_POLICY` убрано
   безадресное `geolocation: ['read']` у `admin`, `parent`, `guardian`.
   Осталось `read_own` / `read_assigned`. Владелец пространства
   привилегии тоже не имеет. Причина: `access_role` в этой БД смешивает
   семейное отношение и полномочие — миграция `V0376` выдала роль
   `parent` 12-летнему участнику.

2. **`scope 'all'` НЕ включает геолокацию.** Подтверждая опекунство,
   человек соглашается вести здоровье и календарь ребёнка. Слежение —
   отдельное решение, и в наборе scopes оно должно быть видно явно,
   иначе аудит не отличит «разрешили слежение» от «разрешили остальное».

3. **Неподтверждённое опекунство не даёт ничего.** Ранее
   `pending_confirmation` давало `read` по `health/medications/children`.
   Послабление снято полностью: гипотеза о родстве, выведенная из роли
   и возраста, не открывает данные ребёнка ни на каком уровне.

4. **Точность старых координат снижается.** Свежая история (14 дней) —
   как есть; старше — округление до 3 знаков (≈110 м). Ответ содержит
   `precision: exact | coarse`, чтобы UI не выдавал округлённое за точное.

5. **Срок хранения объявлен в данных**, а не в комментарии:
   `location_retention_policy` (90 дней хранения, 14 дней точности).
   API не выдаёт историю старше 90 дней.

6. **Отдельный журнал просмотров** `location_access_log` — не смешанный
   с общим `authz_audit_log`, потому что именно его выгружают на вопрос
   «кто видел, где был мой ребёнок».

7. **Отдельное согласие на перемещения** в `member_guardianships`:
   `location_consent_status` (`not_requested` → `requested` → `granted`
   / `declined` / `revoked`).

Закреплено миграциями `V0383`, `V0384` и 80 проверками
`backend/_shared/test_auth_guard.py`, включая:

- `admin` / `parent` / `owner` без связи к координатам ребёнка → 403;
- `scope 'all'` → здоровье да, геолокация нет;
- карта маячка при неподтверждённой связи показывает только себя;
- ни одна роль не имеет безадресного `geolocation: read`.

## 7. Что осталось сделать (не техническое)

> Раздел отражает состояние на момент закрытия уязвимостей.
> Решения по пунктам 3 и 5 приняты — см. разделы 9 и 11.
> Пункты 1, 2 и 4 остаются открытыми.

Требует решения владельца продукта, ответственного за безопасность
и юриста — эти пункты **не** могут быть закрыты разработкой:

1. **Уведомление затронутых семей.** Затронуто 6 семей, 10 человек,
   из них 2 несовершеннолетних. Персональные данные особой категории
   (местоположение ребёнка). Доказать отсутствие утечки нельзя.
   Решение об уведомлении и его формулировка — не инженерное.

2. **Уведомление регулятора.** Оценить, подпадает ли инцидент под
   требование уведомления Роскомнадзора о факте неправомерной передачи
   персональных данных, и в какой срок.

3. **Удаление исторических координат.** 187 точек за период, когда
   доступ был не защищён. Технически удаляются за минуту; решение
   «удалить или сохранить как доказательство» — владельца продукта.

4. **Ретроспектива по логам платформы.** Если у `poehali.dev`
   сохранились логи запросов к функциям за 24.02 — 11.09.2026,
   их следует запросить: это единственный способ получить факты
   вместо «признаков не обнаружено».

5. **Согласие на геолокацию в интерфейсе.** Отдельная кнопка
   подтверждения доступа к перемещениям ребёнка — модель данных
   готова (`location_consent_status`), UI нет.

## 8. Процессные выводы

Три из пяти geo-функций не имели аутентификации, и это не было замечено
ни code review, ни тестами, ни мониторингом. Почему:

- **тест закреплял утечку.** `tests.json` функции `location-history`
  ожидал `200` без токена. Тест не забыли — его написали, зафиксировав
  неверное поведение как правильное. Отсюда правило: для каждого
  чувствительного эндпоинта обязателен негативный тест «без токена → 401»,
  и `scripts/check-deploy-manifest.mjs --smoke` проверяет это против
  продакшена после каждого релиза.

- **`geofence-notifications` «работала»**, потому что возвращала `200`
  на `POST`. Фактически она падала на каждом запросе с неверными
  колонками. Успешный `200` ничего не подтверждал.

- **аудита не было.** За 199 дней ни одна запись о доступе к геоданным
  не сохранилась. Теперь доступ к чужим координатам журналируется
  внутри guard-а, а не по усмотрению вызывающей функции.

## 9. Принятые решения (11.09.2026)

Ниже — то, что решено и исполнено, отдельно от того, что осталось
открытым. Раздел 7 («что осталось сделать») закрыт не полностью:
пункты 1, 2 и 4 сознательно оставлены открытыми, см. раздел 11.

### 9.1 Исправления доступа сохранены

Доступ к геоданным без сессии невозможен ни на одном эндпоинте.
Проверено против продакшена после релиза (`--smoke`, без токена):

```
location-history        401 NO_SESSION_TOKEN
family-tracker          401 NO_SESSION_TOKEN
family-tracker-members  401 NO_SESSION_TOKEN
geofences               401 NO_SESSION_TOKEN
geofence-notifications  403 (без cron-секрета)
```

### 9.2 Геолокация выключена

Функция остаётся выключенной **до появления отдельного согласия
на перемещения и интерфейса управления этим доступом**. Причина не в
том, что уязвимость не закрыта — она закрыта, — а в том, что человек
до сих пор не может увидеть, кто имеет доступ к его перемещениям, и
отозвать этот доступ. Модель данных согласия готова (`V0384`,
`location_consent_status`), интерфейса нет. Пока его нет, сбор
координат не возобновляется.

Выключатель продублирован на трёх уровнях намеренно — отказ одного
не должен возобновить сбор:

| Уровень | Механизм | Поведение |
|---|---|---|
| БД | `feature_flags`: `family_tracker_enabled`, `geolocation_collection_enabled`, `geolocation_history_enabled` = `false` | источник истины |
| Backend | `auth_guard.require_geo_enabled()` внутри `require_location_access()` | `503 GEOLOCATION_DISABLED` |
| Frontend | `GEOLOCATION_DISABLED` в `useFamilyTracker` | GPS у пользователя не запрашивается |
| Service worker | `sw.js` v15, `GEOLOCATION_DISABLED` | фоновый сбор гасится при активации |

Два обстоятельства, из-за которых серверного отказа было бы мало:

1. **Service worker уже работал у части пользователей.** Он будил
   вкладки и запрашивал GPS каждые 10 минут. Сервер перестал бы
   принимать точки, но у человека на устройстве местоположение
   продолжали бы запрашивать. Поэтому версия воркера поднята до v15,
   и при активации он гасит свой таймер.
2. **`localStorage.isTracking=true`** сам возобновлял сбор при
   загрузке страницы. Теперь это состояние стирается.

Проверка флага — **fail-closed**: отсутствие флага, ошибка БД или
пустой ответ трактуются как «выключено». Недоступность базы не должна
оказаться способом снова включить сбор координат.

### 9.3 187 точек заблокированы, но не удалены

`family_location_tracking.usage_status = 'blocked_incident'` для всех
187 строк, `blocked_reason` и `blocked_at` заполнены. Приложение их
не использует: фильтр `usage_status = 'active'` стоит в запросах
`family-tracker` и `location-history`.

Удаления нет: точки — доказательство по инциденту. Чтобы их не снесла
автоматическая очистка по retention, в `location_retention_policy`
выставлен `legal_hold = true`. Решение об удалении принимается
отдельно, после закрытия карточки.

### 9.4 Что видит пользователь

Раздел «Семейный маячок» не притворяется работающим. Кнопка «Включить
отслеживание» убрана, а не сделана неактивной: неактивная кнопка всё
равно обещает функцию. Вместо неё — прямое объяснение, что сбор
остановлен и ранее собранные координаты не используются. Страница
`/location-history` — та самая, что отдавала треки детей без
авторизации, — данных не запрашивает вообще.

### 10.3 Результаты тестов

```

```

Из них по геолокации:

- `admin` / `parent` / `owner` без связи к координатам ребёнка → 403;
- `scope 'all'` → здоровье да, геолокация нет;
- ни одна роль не имеет безадресного `geolocation: read`;
- карта маячка при неподтверждённой связи показывает только себя;
- геолокация выключена: даже явный scope → 503;
- геолокация выключена: свои координаты тоже → 503;
- неизвестный geo-флаг трактуется как выключенный.

Последние три добавлены этой волной. Тесты модели прав намеренно
выполняются при **включённом** выключателе: иначе «доступ запрещён»
было бы не отличить от «функция приостановлена», и тесты перестали бы
доказывать, что права работают. Выключатель проверяется отдельно.

## 11. Что сознательно НЕ сделано

Не «забыто» и не «отложено до лучших времён» — решено не делать
сейчас, с указанием, при каких условиях решение пересматривается.

| Решение | Формулировка | Пересмотр |
|---|---|---|
| Уведомление семей | Сообщения затронутым семьям сейчас не отправляем | При любом признаке эксплуатации; при решении юриста |
| Публичное сообщение | Самостоятельно об инциденте публично не сообщаем | То же |
| Уведомление регулятора | Оценка остаётся за ответственным за безопасность и юристом | Не закрыто |
| Удаление 187 точек | Не удаляем, держим под `legal_hold` | После закрытия карточки |
| Запрос логов у платформы | Остаётся открытым (раздел 7, п. 4) | Единственный способ получить факты вместо «признаков не обнаружено» |

Основание для решений: 6 семей, 10 человек, 2 несовершеннолетних;
**подтверждённых обращений посторонних не обнаружено**; при этом
**отсутствие логов за период уязвимости не позволяет полностью
исключить такой доступ**. Обе формулировки обязаны идти рядом:
«не обнаружено» здесь означает отсутствие данных, а не отсутствие
события, и подменять одно другим в этой карточке нельзя.

Что делает решения обратимыми: геолокация выключена, новые данные
не собираются, исторические точки заблокированы и сохранены. Если
появится факт эксплуатации — есть и данные для оценки, и техническая
возможность уведомить.

## 12. Подсистема согласий (12.09.2026)

Условие возврата геолокации: она не включается обратно как была, а
только через отдельное информированное согласие. Ниже — что уже
сделано и что осталось до включения флагов.

### 12.1 Почему тумблера недостаточно

Тумблер «включить отслеживание» согласием не является:

- **ч.1.1 ст.9 152-ФЗ** — согласие не может быть частью другого
  документа (оферты, пользовательского соглашения) и должно быть
  отдельным актом;
- **конкретность** — согласие даётся на конкретную цель, перечень
  данных и срок. «Включить геолокацию» этих условий не содержит;
- **субъект ≠ нажавший** — включить отслеживание ребёнка хочет
  родитель, но согласие должен дать субъект данных или его законный
  представитель.

Поэтому тумблер только ОТКРЫВАЕТ экран согласия. Сбор начинается
после того, как сервер записал согласие, и ни секундой раньше.

### 12.2 Принятые продуктовые решения

| Вопрос | Решение |
|---|---|
| Дети | до 14 — подтверждённый законный представитель; с 14 — только сам субъект; возраст неизвестен — не включать |
| 187 старых точек | удалить после снятия `legal_hold`, дату зафиксировать; новое согласие их не легализует |
| Срок хранения | выбирает пользователь: не хранить / 7 / 30 / 90 дней, по умолчанию 7 |
| Срок согласия | бессрочно до отзыва + напоминание раз в год (не продлевает автоматически) |

### 12.3 Модель данных (V0386–V0388)

| Таблица | Назначение |
|---|---|
| `location_consent_texts` | версионированные тексты; без них через год не доказать, ЧТО человек читал |
| `location_consents` | согласие субъекта: роль давшего, возраст на момент выдачи, состав данных, срок хранения |
| `location_consent_recipients` | кто именно может видеть; согласие без получателя не открывает координаты никому |
| `location_consent_events` | неизменяемый журнал: выдача, отказ, отзыв |
| `legal_representatives` | подтверждённое законное представительство |

Ключевое разделение, которое нельзя нарушать:

```
согласие субъекта   → системе разрешено СОБИРАТЬ его местоположение
scope 'geolocation' → конкретному человеку разрешено его СМОТРЕТЬ
```

Ни одно не заменяет другое. Право смотреть не создаёт основания
обрабатывать, а согласие не открывает координаты всем подряд.

### 12.4 Серверный шлюз

`require_location_consent()` встроен ВНУТРЬ `require_location_access()`,
то есть на единственном законном входе к геоданным. Новая гео-функция
не может обойти согласие, просто забыв о нём, — тот же приём, что
применён с флагом выключателя.

Дополнительно:

- `accessible_subject_ids('geolocation')` фильтрует по согласию —
  списковый путь не расходится с одиночным;
- запись координат (`family-tracker` POST) требует согласия САМОГО
  актора и проставляет `purge_after` из выбранного им срока;
- согласие представителя **само прекращает действие**, когда ребёнку
  исполняется 14 — проверка на каждом обращении, а не раз в сутки
  по расписанию: иначе между днём рождения и запуском задачи данные
  собирались бы без основания;
- **возраст неизвестен → отказ**. У 96 из 130 участников возраст сейчас
  не указан, и молча считать их взрослыми нельзя: именно так ребёнок
  и получил бы режим взрослого.

### 12.5 Физическая очистка

`location-retention-cron` — новая функция, закрытая `CRON_SECRET`.

До неё срок хранения был декларацией: цифры лежали в
`location_retention_policy`, `location-history` огрублял координаты при
чтении, но физически данные оставались в базе навсегда. Огрубление на
чтении — не удаление: полные координаты продолжали храниться и
продолжали быть тем, что утекает при следующем инциденте.

Никогда не удаляет автоматически: точки под `blocked_incident`
(SEC-2026-001) и всё при `legal_hold = true`. Юридическое удержание
сильнее политики хранения.

### 12.6 Интерфейс

- тумблер открывает экран согласия; заранее проставленных галочек нет;
- на экране видно: чьё положение, состав данных, точность, частота,
  фон, получатели, срок хранения, способ отзыва, правовое основание;
- кнопка называет действие прямо: «Даю согласие и включаю»;
- **оптимистичного включения нет** — при ошибке записи согласия GPS
  и service worker не запускаются;
- автовозобновление сбора по `localStorage.isTracking` убрано: согласие
  могло быть отозвано с другого устройства или прекратиться само,
  а локальный флаг об этом не знает;
- отключение = остановка сбора + отзыв согласия на сервере.

### 12.7 Что осталось до включения флагов

Флаги `geolocation_collection_enabled` / `geolocation_history_enabled`
остаются **выключенными**. До включения:

1. UI подтверждения законного представительства (таблица есть, экрана нет);
2. экран «кто видит моё местоположение» — данные отдаёт `location-consent` GET;
3. ежегодное напоминание (поле `next_reminder_at` есть, рассылки нет);
4. заполнение возраста участников — иначе включить нельзя никому из 96;
5. регламент запуска `location-retention-cron`;
6. QA-цикл на тестовой семье;
7. **утверждение юристом** возрастной модели и текста согласия.

### 12.8 Оговорка

Выполнены инженерные меры. Возрастная модель (14 лет) — консервативная
техническая интерпретация дееспособности по ГК РФ, а не установленный
152-ФЗ порог согласия на обработку персональных данных. Текст согласия
хранится со статусом `pending_legal_review`. Утверждение возрастной
модели и финальной редакции текста — за профильным юристом; называть
реализацию «полностью соответствующей закону» до этого нельзя.
