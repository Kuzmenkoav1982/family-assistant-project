# Серверная авторизация: состояние и план

Документ ведётся по мере миграции. Источник истины по правам —
`backend/_shared/auth_guard.py` (`ROLE_POLICY`, `POLICY_VERSION`).

## Принцип

```
require_session      → кто выполняет запрос (только sessions.token)
require_permission   → может ли роль в принципе (RBAC)
require_same_family  → объект относится к моей семье (IDOR/BOLA)
require_subject_access → доступ к данным именно этого человека (ABAC)
```

Default deny. `X-User-Id` больше не identity: допустим только как
requested member через `resolve_requested_member()`, всегда проверяется.

Владение семьёй отделено от роли: `families.owner_user_id`. Только владелец
удаляет семью, передаёт владение и запрашивает полный экспорт. Обычный
`admin` этого не может, и `admin` НЕ получает автоматического доступа
к здоровью и финансам участников — нужна явная связь `member_guardianships`
или родительство над ребёнком.

### Опекунства: backfill ≠ подтверждённое родство

неподтверждённых подопечных не возвращает.

### Владение

`ownership_source` + `ownership_confirmed`. Единственная семья с
fallback-владельцем (`046e1a53`) помечена `migration_fallback`,

### Пустые пространства

## Волна 4 — геолокация (SEC-2026-001)

Полная карточка: `audit/incident-SEC-2026-001-geolocation.md`.

Проверка всего geo-блока нашла ещё **три** функции без аутентификации —
`location-history` была не единственной:

| Функция | Что отдавала без токена |
|---|---|
| `geofences` | `GET` — геозоны **всех семей** (дом, школа, садик как координаты с названиями); `DELETE ?id=<int>` — удаление любой зоны перебором; `POST` — создание зоны без `family_id` |
| `geofence-notifications` | `POST` — запуск рассылки; адресаты выбирались **без `family_id`**, то есть «вышел из зоны Школа» ушло бы чужим семьям |
| `family-tracker` | сверка координат с геозонами **всех** семей; список всех участников без адресной проверки |

`geofence-notifications` фактически не сработала только потому, что
обращалась к несуществующим колонкам и падала в 500. Это не защита.

`geofences/tests.json` — второй случай теста, закреплявшего утечку:
«Get geofences list» ожидал `200` без токена.

### Масштаб

187 точек, 10 пользователей, 6 семей, 24.02 — 11.09.2026 (199 дней
реального окна; первые 6 недель функция падала на `int(uuid)`).
Среди субъектов **двое несовершеннолетних** (12 и 5 лет). Точность
до 10 м — «координаты были приблизительными» сказать нельзя.

Признаков эксплуатации не найдено, но **доказать их отсутствие
невозможно**: журналов запросов за период нет. `authz_audit_log` начат
09.09.2026, `rate_limit_log` фиксирует только `auth`.

### Новая политика доступа к перемещениям

```
сессия + своя семья + активный субъект
  + (я сам ИЛИ подтверждённая связь с ЯВНЫМ scope 'geolocation')
  + запись в аудит
```

`auth_guard.require_location_access()` — единственный законный вход.

Изменено принципиально:

1. **Роль не открывает координаты.** Из `ROLE_POLICY` убрано безадресное
   `geolocation: ['read']` у `admin`, `parent`, `guardian`. Владелец
   пространства привилегии тоже не имеет.
2. **`scope 'all'` НЕ включает геолокацию.** Согласие вести здоровье
   ребёнка — не согласие на слежение; в наборе scopes это должно быть
   видно явно, иначе аудит не различит два разных решения.
3. **Неподтверждённое опекунство не даёт ничего.** Прежнее послабление
   (`read` по `health/medications/children` для `pending_confirmation`)
   снято полностью: гипотеза о родстве, выведенная из роли и возраста,
   не открывает данные ребёнка ни на каком уровне.
4. **Раздельные scopes**: `health:read` / `health:write` /
   `geolocation:read`. Legacy-форма без уточнения равна `:write`.
5. **Точность старых координат снижается**: 14 дней как есть, дальше
   округление до ≈110 м. Ответ несёт `precision: exact | coarse`.
6. **Срок хранения в данных**, не в комментарии:
   `location_retention_policy` (90 / 14 дней).
7. **Отдельный журнал** `location_access_log` — его выгружают на вопрос
   «кто видел, где был мой ребёнок».
8. **Отдельное согласие** `member_guardianships.location_consent_status`.

Закреплено V0383, V0384 и 80 проверками (было 60), включая
`admin`/`parent`/`owner` без связи → 403, `scope 'all'` → здоровье да /
геолокация нет, «ни одна роль не имеет безадресного `geolocation:read`».

### Деплой

Манифест снова отработал: после первого прохода 14 функций (включая
`auth-me`, `family-members`, `payment-sbp`) выпали из `func2url.json`
по таймауту платформы. Все были живы по прежним URL — то есть карта
теряется отдельно от функций. Восстановлены передеплоем, карту вручную
не правил. Smoke расширен на весь geo-блок и на cron-обработчики.

### Осталось не инженерное

Уведомление 6 семей, уведомление регулятора, судьба 187 исторических
точек, запрос логов платформы за 199 дней, UI подтверждения согласия
на геолокацию. Детали — в карточке инцидента.

удалить `resolve_requested_member()`, убрать заголовок из CORS,
добавить в CI запрет на любое упоминание заголовка.

## Аудит

Таблица `authz_audit_log`. Пишутся: кто, семья, роль, модуль, действие,
тип и id ресурса, результат, `reason_code`, статус, хеш IP, семейство UA.
НЕ пишутся: диагнозы, тексты, показатели, номера документов, реквизиты,
токены, тела запросов.

Отдельная от `security_audit_log`, потому что там `user_id INTEGER`,
а `users.id` — UUID.

Не забыть установить: срок хранения, круг доступа, защиту от изменения,
регламент выгрузки инцидентов. Есть заготовка `authz_denial_counters`
для схлопывания одинаковых отказов, чтобы журнал нельзя было переполнить.

## Известная аномалия KE-health

`health_profiles.user_id` и `doctors.user_id` физически хранят
`family_members.id`, а не `users.id`. На аутентификацию это больше не влияет
(сервер сам сопоставляет сессию с `member_id`), но при любых JOIN учитывать.
